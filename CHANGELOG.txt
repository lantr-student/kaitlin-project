Spotter — Change Log
Major changes are logged here going forward, most recent first. The dated
log below documents each day's changes. 
The "Main changes from original" section further down is a living summary of
the site's current state — it's edited/pruned as features change or get
removed, so it never mentions anything that no longer exists.

================================================================================

2026-08-15
- Audited plan generation for LLM-call count, token size, and missing
  validation (backend/main.py). Call count and candidate-filtering were
  already optimal from the 2026-08-13 fix (1 LLM call, 0-1 retries, no
  tool loop, candidates pre-filtered in Python) — no change needed there.
  Found and fixed three real issues: (1) PLAN_SYSTEM_PROMPT was splicing
  in the entire chat SYSTEM_PROMPT, including instructions to use the
  lookup_exercise tool and format for the chat UI — both irrelevant since
  plan_llm has no tools bound and returns structured data, not chat text.
  Split the shared persona text into a new COACH_PERSONA constant that
  both prompts build from, so the plan prompt drops the dead instructions
  (measured: system prompt 3054 -> 2659 chars, ~78 fewer input tokens per
  call in testing) while chat's SYSTEM_PROMPT stays byte-for-byte
  unchanged. (2) Nothing checked that the model's returned exercise names
  actually matched the candidate list it was offered — a hallucinated or
  off-candidate name (e.g. wrong equipment/experience tier) would have
  shipped straight to the frontend silently. Added _validate_plan_exercises,
  which checks every non-rest-day exercise against the exact candidates
  offered and rejects same-day duplicates; failures go through the
  existing retry-then-502 path, same as the pre-existing day-order/count
  check. (3) TimingCallback only logged prompt character counts, not real
  token usage. It now logs actual input/output/total tokens per call
  (best-effort, degrades to "unavailable" rather than failing if a
  response doesn't carry usage data) plus per-step timing for prompt
  building, the LLM call, and validation, alongside the existing
  total-time/call-count summary.
- Replaced hand-curated substitutes/progression/regression lists with a
  computed weighted-similarity engine (backend/exercise_library.py):
  ranks every other exercise against a target by primary-muscle overlap
  (40%), movement pattern match (25%), compound/isolation match (15%),
  secondary-muscle overlap (10%), and skill/stability closeness (10%),
  then picks the closest matches — restricted to strictly harder ones
  for progression, strictly easier for regression. The three fields are
  gone from exercises.json entirely; nothing is hand-authored anymore.
  lookup_exercise now computes these live. Since the Log page's Swap
  menu used to read substitutes straight out of the local JSON file
  (no network call), it now calls a new GET /exercises/{name}/relations
  endpoint instead (lib/api.ts's fetchExerciseRelations, fetched async
  on page load per exercise, with a small static fallback list if that
  call fails). Exercises already at the top of a muscle group's
  difficulty range (e.g. Back Squat, Deadlift) have nothing in the data
  our 3-tier difficulty model considers strictly harder, so
  compute_progression falls back to the closest same-difficulty
  options instead of returning nothing (e.g. Pause Squat/Front Squat
  for Back Squat) — flagged via a new is_same_difficulty field so nothing
  claims a lateral pick is "harder" than it is. The coach's own wording
  reflects this correctly in testing ("the library doesn't have a
  direct harder progression... but here are the best options").
  Also found and fixed a pre-existing bug (unrelated to this change,
  just newly easy to hit now that substitutes vary more): the Log
  page's exercise cards keyed on exercise name alone, so swapping to a
  substitute that's already present elsewhere in the day's workout
  produced two cards with the same React key (app/log/page.tsx, both
  the per-exercise progress-ring row and the main exercise cards) —
  confirmed with a live browser test, then fixed by keying on exercise
  index + name together instead, which is always unique and still
  resets each card's edit state when its exercise changes.
  lookup_exercise also gained a direction parameter ("similar" by
  default, or "harder"/"easier") so a plain swap request (equipment
  unavailable, wants variety) only computes/shows the closest same-
  difficulty substitute, and progression/regression only get computed
  at all when the client actually asks for something harder or easier
  — previously every named-exercise lookup always computed and
  surfaced all three regardless of what was actually asked. Confirmed
  in a live conversation that the coach now calls the tool with the
  matching direction for each of the three phrasings.
- Substantially enriched backend/data/exercises.json's schema: muscle_group
  is now primary_muscles, a real list (e.g. Back Squat is Quads AND Glutes,
  not just Quads), plus secondary_muscles; "Full Body" and "Grip/Core" —
  placeholder combo-labels from the original single-muscle schema — are
  gone in favor of the real muscles they stood for (Trap Bar Deadlift is
  now Quads/Hamstrings/Glutes; Farmer's Carry is now Forearms/Core), and
  Glutes/Adductors/Forearms joined the muscle vocabulary as a result. Also
  added movement_pattern (Squat, Hinge, Horizontal Push, etc.),
  exercise_type (Compound/Isolation), stability_demand, skill_demand,
  unilateral, joint_demands, and progression/regression chains (easier
  and harder variants of the same movement, e.g. Back Squat's progression
  is Front Squat/Pause Squat, regression is Goblet Squat) — added 3 new
  exercises (Front Squat, Pause Squat, Preacher Curl) so those chains
  resolve to real entries. lookup_exercise now matches on primary or
  secondary muscle, filters by movement_pattern, and gives a full profile
  (stability/skill demand, joints, progression/regression) for a
  named-exercise lookup, not just its muscle group and substitutes.
  lib/data.ts's type and Swap-label logic were updated for the new list
  shape (multiple primary muscles now join into one label, e.g. "Quads &
  Glutes") — no other frontend changes needed.
  Did a full accuracy pass afterward and fixed several errors: Trap Bar
  Deadlift was marked Advanced despite being the more beginner-friendly
  deadlift variant in real coaching practice (now Intermediate, with a
  proper Advanced conventional Deadlift added above it); Glute Bridge
  listed Hamstrings as a co-primary mover when it's really Glutes-primary
  with Hamstrings assisting; two exercises had equipment that didn't
  match their own name ("Cable Face Pull" was tagged Resistance bands,
  "Kettlebell Swing" was tagged Dumbbells) because Cable machine and
  Kettlebell didn't exist as equipment yet; and a few progression/
  regression links crossed unrelated movement patterns (e.g. Walking
  Lunge listed Goblet Squat as its progression, but lunges and squats
  are different patterns) and were corrected or removed. Equipment
  vocab grew from 8 to 11 items (added Kettlebell, Cable machine, Leg
  machine — reflected in onboarding's equipment picker, lib/data.ts) to
  fix those mismatches properly instead of just renaming exercises, and
  to unlock 16 new popular exercises the old vocab couldn't support:
  Deadlift, Lat Pulldown, Seated Cable Row, Tricep Pushdown, Leg Press,
  Leg Extension, Leg Curl, Bulgarian Split Squat, Step-Up, Dumbbell Fly,
  Arnold Press, Front Raise, Push Press, Bench Dips, Dead Bug, and
  Burpees — bringing the library to 52 exercises total.
- Made backend/data/exercises.json the single source of exercise data
  app-wide. The frontend's separate hand-authored swap-menu alternates
  list is gone — the Log page's Swap option now reads muscle group and
  validated substitutes straight from the same JSON file (imported
  directly, no new API call). Also renamed 5 exercises in the mock
  fallback plan ("Walking Lunges" → "Walking Lunge", "Leg Press" →
  "Glute Bridge", etc.) so every exercise in the app, mock or
  real-generated, now matches a real library entry.
- Gave the coach agent its first tool: lookup_exercise, backed by a new
  authored exercise library (backend/data/exercises.json — 33 exercises
  across all 11 muscle groups, each with equipment, experience level,
  and validated same-muscle-group substitutes). The agent can look up
  an exercise by name or muscle group, filtered by the client's
  equipment and experience level, and pull a legal substitute when a
  movement or piece of equipment isn't available (e.g. the squat rack
  being taken). Every Coach chat reply now ends with a bracketed tag —
  "[lookup_exercise]" or "[no tool]" — showing whether the tool fired,
  and every tool call is logged server-side as
  "tool=lookup_exercise input=<value>" for visibility in Railway's logs.
  Also told the coach to reply in plain text only — it had started
  wrapping exercise names in markdown bold, which the chat UI doesn't
  render, so it was showing up as literal asterisks.

2026-08-13
- Fixed a severe plan-generation slowdown: the LLM was calling the
  lookup_exercise tool many times per plan (often guessing at exercise
  name variants that didn't match), each costing a full extra model
  round-trip — one test run hit 22+ LLM calls and still hadn't finished
  after 90 seconds. Exercises are now filtered deterministically in
  Python by equipment/experience and handed to the model directly, so
  plan generation is a single LLM call (~34s in testing, same 7-day/
  correct-training-day-count output, no invented exercises). Also added
  timing/call-count logging for both /plan and /chat. lookup_exercise
  is unchanged for the chat endpoint's one-off exercise swaps.
- Enabled CORS on the backend API, restricted to the deployed frontend
  origin and localhost — no wildcard.
- Wired the app to the real backend: onboarding now generates a real
  weekly plan via a new /plan endpoint, and Coach chat sends messages
  to /chat and shows the real reply. Progress and Profile still use
  hardcoded data, and state is in-memory only. Also fixed the Plan
  page's "Start workout" button showing up on rest days.
- Polish pass: Plan page header shows the week's date range, Log's
  coach button now says "Talk to coach," and the bottom nav re-centered
  Coach with a tighter, highlighted active tab.
- Redesigned Coach's message bubbles — dropped the "Spotter Coach"
  label, moved the avatar outside the bubble, and replaced the spinner with
  a "thinking" bubble animation while a reply is in flight.
- Replaced each Log page exercise's hover tip popover with a
  click-to-open menu (Form, Why, and Swap — Swap lists three
  alternates targeting that exercise's own muscle group, e.g. Quads
  for Back Squat, from a rough hardcoded pool per muscle group). Also
  removed the Log page's slightly-tilted card look — it was trapping
  the new menu popup behind the next exercise card, and cards are now
  flat instead.
- Reps and weight on the Log page are now read-only until you tap Edit
  on that exercise, which switches its sets to editable fields with
  Save/Cancel; reps clarifications like "each leg" or "sec" stay fixed

- Cleanup pass across today's changes: "today's workout" is now
  resolved once in AppStateProvider and exposed from context instead
  of being recomputed on the Plan and Log pages separately; the
  duplicated set-progress type and a repeated coach-bubble color were
  each consolidated into one shared definition; and the backend now
  reuses one LLM client for both chat and plan generation instead of
  building two.

Main changes from original (current state of the site)
Design system (biggest shift)
- Before: default Tailwind palette (zinc grays, blue-600 accents), system
  font, plain rounded-rectangle cards.
- Now: a custom brand identity — navy #33465C / sage green #7C9270 / warm
  cream #F4F6F7 (with a dedicated dark-mode navy #141A21), Quicksand for
  body text and Caveat (handwriting-style) for accents/headers. All of it
  centralized in lib/theme.ts (didn't exist originally) so every page
  shares the same tokens instead of repeating hex values.
- New shared components built to support this look: Checkbox (hand-sketched
  checkmark), ProgressRing, StickyNote, and a custom icons.tsx set — none
  of these existed in the first prototype.

Landing page
- Went from a centered logo + heading + button on a plain background to a
  full illustrated hero: scattered background rings and faint dumbbell
  watermarks, a much larger logo badge with a custom smiley icon, oversized
  display type, and a bigger CTA button.

Onboarding
- The 6-step wizard (goal → experience → days/week → equipment → dated
  goal → summary) is structurally unchanged from the original — same
  steps, same flow logic.
- Visual revisions: new type scale, the hand-sketch checkbox component,
  and restyled summary rows.
- "Build my plan" now submits the profile to the backend (new /plan
  endpoint), shows a loading state while the plan is generated, and only
  advances to the Plan page once it succeeds — with a retry banner if
  the request fails.

Plan page (largest rewrite — 71 → ~400 lines)
- Originally a simple "today" banner plus a static grid of day cards.
- Now has: time-of-day-aware greeting copy, randomized natural-language
  headlines per day (varies each page load), colored metric progress
  rings, and a three-column layout — one large featured DayCard in the
  center flanked by rows of small day tabs (SmallDayCard) on either side.
  Clicking a small tab swaps that day into the center as the new featured
  card and updates the headline, while hovering one shows a preview flyout
  of its exercises.
- Fixed an off-screen hover-preview tooltip that caused unwanted
  horizontal scrolling on mobile.
- The week shown is now whatever plan the backend generated during
  onboarding (falls back to the original hardcoded week if none has
  been generated yet, e.g. on a fresh page load with no onboarding
  this session).

Log page (91 → ~240 lines)
- Went from a plain list of sets to a "workout notebook" layout — each
  exercise is its own card with a per-exercise options menu, a
  StickyNote-styled coach comment, and per-exercise progress rings.
- Fixed the page being locked to a fixed viewport height, which blocked
  scrolling on small screens.
- Today's workout now comes from the same backend-generated plan as the
  Plan page (same mock fallback when none exists yet).
- Each exercise's lightbulb button opens a small click-to-open menu with
  three options — Form (form tips), Why (why it's in today's plan), and Swap,
  which opens a list of three alternate exercises for that muscle group (with
  a refresh button) to actually replace it.
- Reps and weight are read-only until you tap Edit, which switches that
  exercise's sets into an editable state with Save/Cancel. Reps
  clarifications like "each leg" stay fixed text — only the number is
  editable — and bodyweight exercises with no target weight show no
  weight column at all.

Checking off an exercise on the Plan page bulk-toggles its sets
- AppStateProvider derives exerciseDone automatically (true once every set
  for that exercise is checked) and exposes a separate toggleExercise that
  mass-toggles all of an exercise's sets at once.
- That's what powers the checkbox next to each exercise on the Plan page's
  featured card — checking it there checks every set for that exercise
  without opening the Log page, and the two pages stay in sync since they
  share the same underlying setProgress state.

Progress page
- Added ProgressRing stat tiles and a real trajectory chart (actual-vs-
  target pace line graph), with dot markers on every point along both
  lines, not just the two endpoints.
- Moved the hover tooltip onto the graph as a small floating box, instead
  of a layout-shifting block below the chart.
- Added a second view: a weekly workout-consistency bar chart, with a
  Trajectory/Consistency toggle to switch between the two in the same
  card. Bars run from the goal's start date to its target date — past
  weeks show hardcoded completions, the current week updates live,
  future weeks show the planned pace as a dashed projection.
- Like Log and Coach, the page is now locked to the viewport height on
  desktop (no page-level scroll, chart card flexes to fill remaining
  space); mobile still scrolls normally.

Coach page
- Kept the original chat-bubble concept but restyled the bubbles and
  added a message input box at the bottom.
- The page is locked to the viewport height (h-dvh), with the header and
  input pinned in place; only the message list scrolls internally
  (overflow-y-auto), so the conversation scrolls without the rest of the
  page moving.
- The header now rotates through several short prompts instead of a fixed
  greeting, and the coach's avatar is user-selectable.
- The chat auto-scrolls to the latest message on page load and as new
  messages are sent/received.
- The scripted opening conversation is gone — the screen starts empty,
  and each message you send goes to the real /chat backend endpoint,
  with a pending state while waiting and the real reply appended when
  it arrives (or an inline error if the request fails).
- While waiting for a reply, the Coach avatar icon connects through a small
  circle to a rounded "thinking" bubble with three bouncing dots, which
  resolves into the real reply bubble once it arrives.
- The coach's replies can now call a lookup_exercise tool (backend-side)
  to ground exercise swaps/equipment questions in a real exercise
  library instead of guessing; every reply bubble ends with a bracketed
  "[lookup_exercise]" or "[no tool]" tag showing whether it did.

Profile page (new)
- New page (5th BottomNav tab) with six stat tiles, each with its own
  icon: current streak, longest streak, workouts completed, percent to
  goal, target pace, and total weight moved. Two of those icons
  (a gauge, a loaded barbell) are new, made just for this page.
- Also shows the training profile entered during onboarding (view-only),
  an editable display name, editable login credentials (fake, local-
  only), and a picker for the Coach chat avatar with five new mascot
  icons — shown across the app wherever the coach appears.

Data layer (lib/data.ts)
- Same core shape (goal, plan day, trajectory point, coach turn types),
  but WEEKLY_PLAN's mock content grew substantially (rest times, form
  tips per exercise); it now also serves as the fallback plan whenever
  a real one hasn't been generated yet.
- Added a goalProgressPercent helper to drive the progress rings, and a
  buildWeeklyConsistency helper for the Progress page's bar chart.
- Added an Account type and more streak/volume fields (longestStreakDays,
  totalWorkoutDays, totalWeightLifted) to support the Profile page.
- New lib/api.ts holds the fetch client for the backend (fetchPlan,
  sendChatMessage), used by onboarding and the Coach page.

Backend (kaitlin-project/backend/)
- New FastAPI service (main.py + api.py), deployed on Railway, separate
  from the Next.js frontend. Three endpoints: POST /chat (a LangChain
  agent with a coach persona), POST /plan (LLM-generates a 7-day plan
  from a submitted profile, returned as structured JSON matching the
  frontend's PlanDay[] shape), and GET /exercises/{name}/relations
  (computed substitutes/progression/regression for one exercise, used
  by the Log page's Swap menu).
- The coach agent (POST /chat) has one tool, lookup_exercise, backed by
  an authored exercise library (backend/data/exercises.json) with real
  anatomical primary/secondary muscles, equipment, movement pattern,
  and compound/isolation type — used to ground exercise swaps and
  equipment questions instead of guessing. Substitutes/progression/
  regression aren't stored in that file; backend/exercise_library.py
  computes them from those attributes via a weighted-similarity score,
  shared by the tool and the /exercises/{name}/relations endpoint.
  /plan generation reads from the same library, pre-filtered by
  equipment/experience in Python rather than via tool calls (kept as a
  single LLM call for latency).

What hasn't changed
- Log/set data, Progress, and Profile still run entirely on local state
  and the hardcoded history in lib/data.ts — no persisted workout
  history or real accounts yet.
- Real photo-based form-checking isn't built yet — no photo capture or
  upload exists in the app.
