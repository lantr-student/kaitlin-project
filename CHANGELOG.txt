2026-10-10
- Added a deterministic exercise-selection engine (backend/exercise_selection.py)
  that fills every exercise slot from workout_structure.py's output with a real
  exercise from the library — the next stage of the rules-based plan-generation
  pipeline, after training_prescription.py and workout_structure.py. For each
  slot it filters the library by exercise type (compound/isolation), target
  muscle, equipment, experience level, and a client's avoid-list (the same
  constraints list training_prescription.py already uses, now also matched
  against exercise names), then scores survivors by muscle match (primary
  muscle scores full weight, secondary-only scores half), a goal-based bonus
  (compound-favoring for Build strength, low-skill/low-stability-favoring for
  Lose fat/Improve endurance, neutral for Build muscle/Improve Overall
  Fitness), and picks the highest scorer — ties broken by fewest secondary
  muscles, then alphabetically, so output is fully deterministic. An exercise
  never repeats within the same day's slots (repeats across different days
  are fine), and no two slots on the same day share a movement pattern unless
  nothing else is available. When a slot's filters come up empty, relaxes
  constraints in a fixed order — drop movement-pattern variety, then allow
  one experience level above the client's, then allow equipment the client
  doesn't have — with a flat score penalty per relaxation level
  (backend/training_rules.py's new RELAXATION_PENALTY_BY_LEVEL); target
  muscle and the avoid-list are never relaxed. If even that comes up empty
  (a genuine library gap), the slot is reported as explicitly unfilled with a
  reason rather than left blank or invented. New tests
  (backend/tests/test_exercise_selection.py) cover each filter independently,
  the scoring weights, same-day no-repeat/cross-day repeat behavior, movement-
  pattern variety and its relaxation, fallback escalation through all three
  levels, the genuine-gap case, tie-break determinism, and two end-to-end
  profiles run through the full Stage 1 → 2 → 3 pipeline. Standalone for
  now — not yet wired into /plan generation.
- Reviewed Stages 1-3 end to end to confirm they work as one connected
  pipeline rather than three independent pieces: swept every goal ×
  experience level × day-count × equipment combination through all three
  stages (no exceptions anywhere) and confirmed training_prescription.py,
  exercise_library.py, and exercise_selection.py all agree exactly on the
  same goal/experience-level/muscle-group vocabulary, and that a muscle
  excluded via a constraint correctly disappears from every stage's output
  with no leftover references. Added compute_full_plan (backend/
  exercise_selection.py) as a single entry point that runs all three stages
  from one input object, so goal/experience/equipment/constraints are read
  once and can't end up inconsistent between stages. New regression tests
  cover the chained pipeline, exclusion propagation, the cross-stage
  vocabulary match, and a full-matrix no-crash sweep. No changes needed to
  training_prescription.py or workout_structure.py — the only gap was the
  lack of a single entry point, now closed. (Two non-bugs noted and
  deliberately left alone: a few muscle/type combos have only one matching
  exercise in the library, e.g. Quads has just one Isolation exercise,
  which Stage 3 already reports as honestly unfilled rather than inventing
  one; and under very restrictive equipment, which of two contending
  muscles gets left unfilled can depend on slot processing order — the
  total number of unfillable slots is unaffected either way, and fixing
  the order-dependence would require a global per-day matching algorithm,
  out of scope for this pass.)
- Added a deterministic sets/reps/starting-weight engine (backend/
  exercise_prescription.py) — Stage 4 of the rules-based plan-generation
  pipeline, attaching a full prescription to every exercise Stage 3 already
  selected. Sets and reps are a config lookup by goal and by the exercise's
  existing Compound/Isolation type (backend/training_rules.py's new
  GOAL_ROLE_SETS_REPS — seeded for Build muscle with 3x6-10 for compound
  lifts and 3x10-15 for isolation work; the other four goals are first-pass
  placeholders flagged for review). Weight recommendation tries three
  things in order: bodyweight exercises always get no weight to track;
  logged history for that exact exercise goes through the existing
  progression_calculator (Stage 6) unchanged; with no history for the
  exercise itself, it looks for the client's most similar already-logged
  exercise that uses the exact same equipment (reusing exercise_library's
  existing similarity scorer, restricted to same equipment so the number
  stays on a sensible scale — no fabricated cross-equipment conversion),
  and estimates a starting weight at 60% of that exercise's estimated
  1-rep max (new STARTING_WEIGHT_PERCENT_OF_SIMILAR_1RM, flagged for
  review); if neither exists, falls back to a flat default by exercise
  type and experience level (new STARTING_WEIGHT_FALLBACK_LB, also flagged
  for review). Every recommendation is just that — a recommendation; the
  client can log whatever weight they actually use, and the next time that
  exercise comes up it has real history and moves to the history tier
  automatically, no new feedback mechanism needed beyond what already
  exists. New tests (backend/tests/test_exercise_prescription.py) cover
  the config lookup and that editing it changes the output, each weight
  tier independently (including the same-equipment requirement correctly
  blocking a same-muscle/different-equipment match), and an end-to-end run
  through the full Stage 1 → 2 → 3 → 4 pipeline. Standalone for now — not
  yet wired into /plan generation.

- Added a deterministic plan-validation gate (backend/plan_validation.py) —
  Stage 5 of the rules-based plan-generation pipeline, the final check
  every plan passes through (designed to run after initial generation,
  and later after any adaptation/LLM-patch step revises a plan, though
  neither of those produces a full revised plan yet to actually call it
  on). Checks day count, that every exercise is really in the library, a
  new Pydantic schema for this pipeline's actual output shape, no same-day
  duplicate exercises, sets/reps matching the goal+role config exactly,
  and that every muscle Stage 2 sized a dedicated slot for actually got an
  exercise — any of these failing makes the plan invalid. Equipment
  availability and weekly-volume/session-time ranges are checked too, but
  only as warnings: fallback-resolved slots and volume/time approximations
  are already-accepted tradeoffs of Stage 2/3's design, not signs of a
  broken plan, confirmed by sweeping the full goal x experience x day-count
  matrix under both full and bodyweight-only equipment (zero errors either
  way, just warnings). Caught and fixed a real false positive from a
  stricter first draft of the muscle-coverage check along the way: it was
  flagging muscles like Back/Core/Shoulders as "not covered" on full-body
  days where Stage 2 had deliberately sized zero dedicated slots for them
  because same-day secondary credit already covered their target — the
  check now reads Stage 2's actual intent (did it size a slot at all) using
  backend/workout_structure.py's DaySlot.exercise_slots) rather than
  independently re-deriving which muscles "should" need one. Also fixed
  exercise_prescription.py to carry an unfilled slot through as an explicit
  PrescribedSlot (exercise=None, weight_source="unfilled") instead of
  silently dropping it, since Stage 5's coverage check needs to see it.
  New tests (backend/tests/test_plan_validation.py) mutate one field off a
  real generated plan per check to trigger each error/warning independently,
  plus a real well-equipped plan that passes clean.
- Added a deterministic progression-and-adaptation engine (backend/
  plan_adaptation.py) — Stage 6, which revises an existing plan from
  logged performance instead of regenerating one. Re-runs the same tiered
  weight logic Stage 4 uses (so an exercise naturally moves onto real
  history the moment any exists) and then watches for three adaptation
  signals per exercise: repeated missed reps (3 consecutive sessions
  missing prescribed reps — deloads by one weight increment, escalating
  instead of guessing if that would go to zero or below), stalled progress
  (4 consecutive sessions with no net weight change — swaps the exercise
  for an alternative), and consistently skipped (2+ caller-reported skips —
  same swap treatment). All three threshold counts are new, first-pass
  config in backend/training_rules.py, flagged for review. Exercise swaps
  stay within the limits the Prescription Engine already set: same
  exercise_type (so sets/reps stay valid unchanged), at or below the
  client's experience level, equipment-appropriate, and never a same-day
  duplicate — reusing exercise_library's existing substitute scorer rather
  than building new matching logic. If no safe substitute exists, the
  signal is collected in needs_llm_review instead of forcing a swap — no
  LLM is called for this (or for anything else in this module); that list
  is just what would eventually go to Stage 7. Every candidate revision is
  run back through Stage 5's validate_plan before being returned; if it
  fails, the adaptation is discarded and the original plan is returned
  unchanged with the rejection reason attached, never an invalid plan.
  Also moved WEIGHT_INCREMENT_LB and DEFAULT_WEEKLY_CAP_LB out of
  progression_calculator.py and into training_rules.py per this stage's
  own spec ("increments and caps live in the central config") — no
  behavior change, progression_calculator.py still exposes both names.
  New tests (backend/tests/test_plan_adaptation.py) cover clean
  progression with no signals, the deload path and its escalate-instead-
  of-negative-weight edge case, both swap-triggering signals, a
  below-threshold skip count correctly not firing, no-substitute-found
  escalation, and the revert-on-invalid control flow. Swept every goal x
  experience x day-count combination under worst-case histories (every
  exercise stalled; every exercise missing reps and skipped at once) —
  zero crashes, zero unexpected reverts across 150 combined runs.
  Standalone for now — not yet wired into /sessions.
- Reviewed Stages 1-6 end to end the same way the earlier Stages 1-3 pass
  did, and found two real bugs in Stage 6's exercise-swap path this time
  (both only reachable once a swap actually fires, so the Stage 6 sweeps
  done while building it hadn't forced enough swaps to surface them):
  (1) plan_adaptation.py's substitute search only required sharing *some*
  muscle with the exercise being replaced (primary or secondary, either
  side) rather than specifically the slot's own target muscle — a weak
  secondary-secondary overlap (e.g. Dumbbell Fly and Plank both also touch
  Shoulders) could outrank real alternatives and get chosen despite having
  nothing to do with the muscle the slot exists for, silently breaking
  Stage 1's volume targets and Stage 5's coverage check for that muscle.
  Hit in 268 of 1713 swaps (15.6%) in a full goal x experience x day-count
  sweep. Fixed by requiring the swap candidate to actually match the
  slot's muscle_group (reusing exercise_library's own primary-or-secondary
  match check), confirmed at 0/1569 after the fix across the same sweep.
  (2) The same substitute search never checked the client's avoid-list at
  all, so an adaptation swap could silently reintroduce an exercise the
  client had explicitly excluded, even though Stage 3 never relaxes that
  same constraint during initial generation. Fixed by applying the same
  avoid-list filtering Stage 3 already uses; confirmed at 0 violations
  across a sweep with an active avoid-list. Also added adapt_plan
  (backend/plan_adaptation.py), a single entry point for the full Stages
  1-6 cycle (recomputes the training prescription and workout structure
  from the profile rather than trusting copies a caller might pass in
  mismatched), mirroring compute_full_plan (Stages 1-3) and
  validate_full_plan (Stages 1-5). Extended the existing cross-stage
  vocabulary test (backend/tests/test_exercise_selection.py) to also cover
  Stage 4's goal/role and experience-level config keys. New regression
  tests in backend/tests/test_plan_adaptation.py cover both fixed bugs
  directly. No changes needed to Stages 1-5 — both bugs were contained to
  Stage 6's own substitute-search logic.
- Two small performance fixes to the deterministic pipeline, both verified
  byte-identical output before/after (same SHA-256 hash of every exercise
  picked across the full goal x experience x day-count sweep) and the full
  test suite unchanged: find_exercise (backend/exercise_library.py) was a
  linear scan of the library on every call (used by Stage 4, Stage 5,
  main.py, and api.py) — now an O(1) dict lookup keyed by lowercased name,
  built once at import time. _matches_equipment was re-converting the
  client's equipment list to a set on every single exercise it checked,
  even though that list is constant for an entire call — equipment is now
  converted to a set once per call at every hot-loop site (exercise_
  library.py's _filter_candidates/_candidate_pool, exercise_selection.py's
  compute_exercise_selection, plan_validation.py's _check_equipment)
  instead of inside the per-exercise check itself. Net effect on the
  heaviest case (6-day, Advanced, Build muscle) was modest at today's
  52-exercise library size (~3% faster per plan generated, timeit-measured
  over 500 runs) — the real benefit is that neither cost scales with
  history/library size anymore, where before both would have gotten
  slower as either grew.

2026-08-17
- Fixed unrealistically crowded Upper/Lower training days in
  backend/workout_structure.py: every muscle on a day was getting its full
  independent weekly-share of sets with no credit for the secondary stimulus
  a compound lift already gives other muscles trained the same day (e.g. a
  Chest day's pressing already works Triceps/Shoulders; a Back day's rowing
  already works Biceps/Rear Delts/Forearms) — a 4-day Upper/Lower
  Intermediate/Build-muscle Upper day was coming out to 38-60 total sets.
  Added secondary-muscle volume crediting: derived which (primary, secondary)
  muscle pairings are real and repeatable (>=2 different compound exercises
  agree, filtering out one-off pairings) directly from exercises.json, then
  credit 2 sets per qualifying same-day compound source toward a muscle's own
  target before sizing its dedicated exercise slots (new
  MIN_SECONDARY_COVERAGE_COUNT / SECONDARY_CREDIT_SETS_PER_SOURCE constants
  in backend/training_rules.py). DaySlot now reports target_sets (the full
  weekly-distributed figure, unchanged), secondary_credit_sets, and
  remaining_target_sets (what still needs a dedicated slot — can be zero,
  meaning no dedicated exercise needed that day, e.g. Core on a day already
  full of compound work); day totals (and therefore the over_capacity flag)
  are now based on remaining_target_sets instead of the pre-credit figure.
  Training frequency and weekly volume from training_prescription.py are
  untouched by this — only how a day's dedicated slots get sized changed.
  The hand-verified example above now comes out to 14-34 sets, a ~40% cut.
  New tests cover the crowded-day fix with exact numbers, a fully-credited
  muscle correctly getting no dedicated slot while still being reported,
  credit never going negative across all goals/frequencies, and a muscle
  with no qualifying secondary sources being unaffected.

- Replaced hand-curated substitutes/progression/regression lists with a
  computed weighted-similarity engine (backend/exercise_library.py):
  ranks every other exercise against a target by primary-muscle overlap
  (40%), movement pattern match (25%), compound/isolation match (15%),
  secondary-muscle overlap (10%), and skill/stability closeness (10%),
  then picks the closest matches — restricted to strictly harder ones
  for progression, strictly easier for regression. The three fields are
  gone from exercises.json entirely; nothing is hand-authored anymore.
  lookup_exercise now computes these live. Since the Log page's Swap
  menu used to read substitutes straight out of the local JSON file
  (no network call), it now calls a new GET /exercises/{name}/relations
  endpoint instead (lib/api.ts's fetchExerciseRelations, fetched async
  on page load per exercise, with a small static fallback list if that
  call fails). Exercises already at the top of a muscle group's
  difficulty range (e.g. Back Squat, Deadlift) have nothing in the data
  our 3-tier difficulty model considers strictly harder, so
  compute_progression falls back to the closest same-difficulty
  options instead of returning nothing (e.g. Pause Squat/Front Squat
  for Back Squat) — flagged via a new is_same_difficulty field so nothing
  claims a lateral pick is "harder" than it is. The coach's own wording
  reflects this correctly in testing ("the library doesn't have a
  direct harder progression... but here are the best options").
  Also found and fixed a pre-existing bug (unrelated to this change,
  just newly easy to hit now that substitutes vary more): the Log
  page's exercise cards keyed on exercise name alone, so swapping to a
  substitute that's already present elsewhere in the day's workout
  produced two cards with the same React key (app/log/page.tsx, both
  the per-exercise progress-ring row and the main exercise cards) —
  confirmed with a live browser test, then fixed by keying on exercise
  index + name together instead, which is always unique and still
  resets each card's edit state when its exercise changes.
  lookup_exercise also gained a direction parameter ("similar" by

  difficulty substitute, and progression/regression only get computed
  at all when the client actually asks for something harder or easier

- Added a deterministic progression_calculator tool (backend/progression_calculator.py) so weight progression is computed from logged workout data rather than by LLM arithmetic. It recommends +5 lb after two consecutive sessions completing all prescribed reps at the same weight, repeats the weight when prescribed reps are missed, and otherwise holds the weight. It also estimates current 1RM using the Epley formula, calculates the average lb/week required to reach a target weight by a target date, and checks that rate against the 5 lb/week safety cap.

- Added a workout structure generator (backend/workout_structure.py) that takes a
  TrainingPrescription and distributes it into concrete days: an actual weekday per
  training day (evenly spread with rest days interspersed, via a new TRAINING_WEEKDAYS
  table in backend/training_rules.py), target sets per muscle for that specific day, and
  how many exercise slots of what type (Compound/Isolation) are needed to hit that — still
  without choosing exercises. Weekly volume is split across a muscle's training days with
  an explicit remainder rule (earliest day in the week gets any leftover set, verified to

  frequencies, the remainder/degenerate-case rules with hand-verified numbers, slot typing,
  and both flagging mechanisms actually firing.

Backend (kaitlin-project/backend/)
- New FastAPI service (main.py + api.py), deployed on Railway, separate
  from the Next.js frontend. Endpoints: POST /chat (a LangChain agent
  with a coach persona), POST /plan (LLM-generates a 7-day plan from a
  submitted profile, returned as structured JSON matching the frontend's
  PlanDay[] shape), GET /exercises/{name}/relations (computed
  substitutes/progression/regression for one exercise, used by the Log
  page's Swap menu), and POST /sessions (logs a completed workout
  session for the progression calculator to read back).
- The coach agent (POST /chat) has two tools. lookup_exercise is backed
  by an authored exercise library (backend/data/exercises.json) with
  real anatomical primary/secondary muscles, equipment, movement
  pattern, and compound/isolation type — used to ground exercise swaps
  and equipment questions instead of guessing. Substitutes/progression/
  regression aren't stored in that file; backend/exercise_library.py
  computes them from those attributes via a weighted-similarity score,
  shared by the tool and the /exercises/{name}/relations endpoint.
  /plan generation reads from the same library, pre-filtered by
  equipment/experience in Python rather than via tool calls (kept as a
  single LLM call for latency). progression_calculator
  (backend/progression_calculator.py) deterministically computes the
  next-session weight, an estimated current 1-rep max, and (given a
  goal) the weekly progression needed and whether it exceeds a 5 lb/week
  cap, reading logged sessions from a temporary in-memory store
  (backend/session_store.py — a placeholder until a real database
  exists).
- backend/training_prescription.py deterministically computes the training
  structure a plan should be built around — split/frequency, weekly working-
  sets target and training frequency per muscle group, and rep range — from
  a client's goal/experience/schedule, before any exercises are chosen. All
  the underlying numbers (rep ranges, volume landmarks, split templates)
  live in backend/training_rules.py so they can be retuned without touching
  the logic. Not yet wired into /plan generation — a standalone, tested
  module for now.
- backend/workout_structure.py takes that training prescription and lays it
  out into actual days: a real weekday per training day, target sets per
  muscle for that specific day, and how many exercise slots (and of what
  type — compound vs. isolation) are needed, without picking exercises
  themselves. Credits a muscle's own target with secondary stimulus it
  already gets from other compound work on the same day (derived from real
  secondary-muscle data in exercises.json), so a day's dedicated-slot volume
  reflects realistic session load instead of stacking every muscle's full
  independent share. Also standalone/not yet wired into /plan generation.
- backend/exercise_selection.py fills every slot workout_structure.py sized
  with a real exercise from the library — filtered by type/muscle/equipment/
  experience/avoid-list and scored by muscle/goal match, with a fixed
  constraint-relaxation fallback (and an explicit unfilled result for genuine
  library gaps) so every slot resolves deterministically. Also standalone for
  now.
- backend/exercise_prescription.py attaches sets/reps (goal + compound-vs-
  isolation lookup) and a recommended weight to every exercise Stage 3
  selected — from logged history where it exists, estimated from the most
  similar same-equipment exercise the client has logged where it doesn't,
  or a flat experience-level default as a last resort. Also standalone for
  now.
- backend/plan_validation.py checks a generated plan's day count, exercise
  validity, muscle coverage, duplicate exercises, sets/reps, and output
  schema (hard errors), plus equipment availability and volume/session-time
  ranges (warnings only, since those can legitimately be stretched by
  Stage 2/3's own fallback design). Also standalone for now.
- backend/plan_adaptation.py revises a plan from logged performance:
  updates weights via the same logic Stage 4 uses, deloads after repeated
  missed reps, and swaps an exercise after stalled progress or consistent
  skips — always within Stage 1's limits, always re-validated by Stage 5
  before being applied, reverting to the unchanged plan otherwise. No LLM
  calls; unresolvable situations are only flagged for Stage 7, not acted
  on. Also standalone for now.

Deterministic plan-generation pipeline (backend) — not yet live
A second, fully separate way of building a weekly plan exists alongside
the LLM path described in the Backend section above, built as six
layered, independently-tested modules (246 passing tests total) rather
than one model call:
- training_prescription.py turns goal/experience/days-per-week into a
  split, a weekly min/max set range per muscle, and a rep range — pure
  config lookups, no exercises chosen yet.
- workout_structure.py turns that into real weekdays and sized exercise
  slots per muscle per day, crediting a muscle's target with secondary
  stimulus it already gets from other compound work that same day so
  slot counts reflect realistic session load.
- exercise_selection.py fills every slot with a real exercise, scored by
  muscle/goal match, falling back through a fixed relaxation order
  (movement-pattern variety, then experience, then equipment) rather than
  ever inventing one.
- exercise_prescription.py attaches sets/reps and a weight recommendation
  per exercise — from the client's own logged history where it exists,
  a same-equipment comparable exercise's estimated 1-rep max where it
  doesn't, or a flat experience-level default as a last resort.
- plan_validation.py is the gate every plan passes through: day count,
  real exercises, full muscle coverage, no same-day duplicates, correct
  sets/reps, and a schema check are hard errors; equipment/volume/session-
  time stretches are warnings, since Stage 2/3's own fallback design can
  legitimately produce those without the plan being broken.
- plan_adaptation.py revises an existing plan from logged performance —
  deloads after repeated missed reps, swaps an exercise after stalled
  progress or consistent skips, always re-validated by plan_validation.py
  before being applied and reverted otherwise. No LLM calls anywhere in
  any of this; situations it can't resolve with a clear rule are only
  flagged for a future LLM-patch step, never acted on by calling one.
Measured speed: generating a full plan through all four generation
stages takes about 1.3 ms (worst case: 6-day, Advanced, Build muscle;
timeit, 500 runs) — pure local computation over the 52-exercise library,
no network call. The LLM path's own 2026-08-13 entry above measured
~34 seconds per plan once already down to a single call. That's roughly
26,000x faster for generating the plan's structure, sets, reps, and
weights — not a fully equivalent comparison, since the LLM call also
writes the coach-voice notes and form tips in that same request, which
this pipeline doesn't produce. Not wired into /plan — api.py still calls
the LLM path above for every real request today.

What hasn't changed
- Log/set data, Progress, and Profile still run entirely on local state
  and the hardcoded history in lib/data.ts — no persisted workout
  history or real accounts yet.
- Real photo-based form-checking isn't built yet — no photo capture or
  upload exists in the app.
